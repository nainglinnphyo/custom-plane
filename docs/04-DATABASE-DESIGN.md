# 04 — Database Design (PROPOSED)

Design for PRs 2–6 modules. Nothing is migrated yet. Existing-model facts come from `02-REPOSITORY-ANALYSIS.md`.

## 1. Conventions (mirror upstream)

- Inherit `plane.db.models.base.BaseModel` (UUID PK, audit fields, soft delete) — via `WorkspaceBaseModel` when workspace-scoped, `ProjectBaseModel` when project-scoped. **Do not** use `BigAutoField` for business models.
- Explicit `db_table = "custom_<module>_<entity>"`; unique constraints follow upstream's pattern: `unique_together` including `deleted_at` **and** a partial `UniqueConstraint(condition=Q(deleted_at__isnull=True))`.
- One Django app per module with a distinct `label` (`custom_company`, …); migrations are additive; **no migration touches a core table**.
- Foreign keys to core use string refs (`"db.Workspace"`, `"db.Issue"`, `settings.AUTH_USER_MODEL`) and `on_delete` chosen per row; `related_name` prefixed `custom_…` to avoid reverse-accessor clashes on core models.
- Lockfile (`apps/api/migrations_lockfile.txt`) is regenerated by `makemigrations`; commit it, never edit by hand.

## 2. Module 1–2: Departments, teams (no Company entity, see D9)

| Model              | Fields (beyond base)                                                              | Constraints / notes                                                                        |
| ------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `Department`       | `workspace` FK, `name`, `description`, `parent` self-FK null, `head` FK User null | unique (workspace, parent, name); cycle check in service layer                             |
| `DepartmentMember` | `department` FK, `member` FK User, `role` (member/lead)                           | unique (department, member); member must be an active `WorkspaceMember` (service-enforced) |
| `CustomTeam`       | `workspace` FK, `name`, `description`, `department` FK null (SET_NULL)            | unique (workspace, name); table `custom_teams`                                             |
| `TeamMember`       | `team` FK, `member` FK User, `role` (member/lead)                                 | unique (team, member); member must be an active `WorkspaceMember` (service-enforced)       |

**Implemented in PR 3** (apps `custom_company`, `custom_teams`; tables `custom_departments`, `custom_department_members`, `custom_teams`, `custom_team_members`). Differences from the first design: **there is no `Company` / `CompanyWorkspace` model** — a workspace _is_ the company (decision D9); `Department.head` was dropped in favour of `DepartmentMember.role = lead` (several leads allowed); `CustomTeam` is a separate table, not the dormant upstream `db.Team` (D8); department nesting is limited to 8 levels; workspace-scoped models use `BaseModel` + an explicit `workspace` FK rather than `WorkspaceBaseModel`, which carries an unused nullable `project` column. The app label stays `custom_company` for the departments app (renaming would churn migrations and routes).

## 4. Module 4: Milestones

| Model                 | Fields                                                                                                                                       | Notes                                               |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `Milestone`           | `project` FK, `name`, `description`, `start_date`, `due_date`, `status` (planned/in_progress/achieved/missed), `owner` FK User, `sort_order` | `due_date >= start_date` CHECK                      |
| `MilestoneIssue`      | `milestone` FK, `issue` FK                                                                                                                   | unique (milestone, issue)                           |
| `MilestoneDependency` | `milestone` FK, `depends_on` FK, `type` (finish_to_start, …)                                                                                 | no self-dependency CHECK; DAG validation in service |

Reuse: `Issue.start_date/target_date` (DateField), `IssueRelation` types (`blocked_by`, `start_before`, `finish_before`) are the vocabulary for dependencies. `Module` is _not_ used as the milestone table because it has its own lifecycle/UI and would couple to upstream.

## 5. Module 5: Timesheets

## 8. Indexing & performance

Composite indexes on `(workspace, user, period_start)` (timesheets), `(project, due_date)` (milestones), `(request, order)` (steps), `(user, started_at)` (entries). Report queries should honor the read-replica switch (`ReadReplicaControlMixin`).

## 9. Risks

- FKs from custom tables to core tables mean a future upstream rename/removal of a core model breaks custom migrations — pin by checking `makemigrations --check` after each upstream merge.
- Soft-delete cascades (`soft_delete_related_objects`) are generic and should cover custom models that inherit `BaseModel` — verify with a test in PR 2.
